# Submission requests and collaboration

Signed-in, approved users have **File requests** and **Collaborations** tabs. Create an invitation with recipient email addresses, expiry, storage destination and size limits. You can email it automatically or copy its link/access code. Management shows links, submissions and revocation controls; administrators can view all users' invitations. Download shares continue to work.

The home access form accepts download keys, submission keys (`U…`) and collaboration keys (`C…`). Possessing the code is insufficient: the recipient must verify a PIN delivered to an invited email. External recipients require no approved File Station account. Sessions and every subsequent operation check invitation expiry, revocation and owner status.

Submission partners can upload to the requester-selected connector. They see only their own submissions, with no access to other recipients' files, destination credentials, file listings or download access. File-count and size limits are enforced server-side. Quota/retention apply to submitted files as to ordinary uploads, and the requester owns them.

For collaboration, select an uploaded original and specify a target filename with the same extension. The original remains unchanged. Until the first save, downloads use its bytes with the target name. Saves and re-uploads publish one separate working copy. Subsequent saves replace that working copy and delete the previous one. There is **no version history** or simultaneous keystroke synchronization. Concurrent saves use a compare-and-swap token so a stale editor cannot silently overwrite another person's changes. Download your local edits if a conflict occurs, reopen the current copy, and merge them.

DOCX and UTF-8 plain text (including Markdown/CSV/JSON/XML/YAML) up to 20 MiB can be edited in the browser. DOCX uses the Apache-licensed EigenPal editor; complex Word features may render differently, so review documents in Word when layout fidelity is critical. The editor is loaded on demand, uses local fonts and does not send documents to Microsoft 365 or an external editor server. Larger or unsupported documents can be downloaded, edited on a desktop and re-uploaded. Edits are saved only when **Save working copy** finishes its transfer; unsaved browser edits do not survive refresh. Transfers themselves support pause/resume.

Active collaboration originals and current copies are protected from FIFO eviction so a save cannot evict its own original. There must be space for the old copy and the incoming replacement during a save. Age retention, explicit deletion and owner deactivation can still invalidate collaboration. Expired/revoked links do not grant perpetual access.

## File previews

Verified download recipients and collaboration partners have an inline preview. Images (PNG, JPEG, GIF, WebP, AVIF, BMP), browser-supported video/audio, PDF, DOCX and UTF-8 text are supported. Markdown, CSV, JSON, XML, HTML and SVG appear as escaped source text; uploaded markup never executes. Other formats, including legacy Office documents, spreadsheets, presentations and archives, retain their download options.

Small files up to 10 MiB open automatically. Larger supported files require **Show preview**. Image previews are limited to 25 MiB, PDFs to 50 MiB, DOCX to 20 MiB and text to 2 MiB. Video/audio use authenticated byte ranges capped at 8 MiB per response, including seeking on WebDAV-backed storage. Playback depends on the browser's codecs. Hide preview to stop loading or playback. Downloads remain available when a renderer fails or a file is too large.

PDF pages render locally with PDF.js, with page navigation, zoom and an accessible page-text option. DOCX uses the existing editor in read-only mode. Preview code, fonts and PDF resources are served from File Station; no external document viewer receives the files. Every preview/range request rechecks the same recipient authorization, retention and expiry rules as downloading. A collaboration preview refreshes after a saved edit or re-upload, and refuses to show a replacement under an older file identity. Already displayed bytes cannot be withdrawn from a recipient's browser by revoking access.

## Parallel transfers

The transfer panel lets each browser choose **1–3 parallel connections**, with three by default and a shared limit of six active chunk requests across its transfers. A change applies to new or resumed transfers. Use fewer connections for constrained networks. R2, S3, AliPan and WebDAV/Synology uploads can send independent chunks together. Microsoft requires OneDrive upload-session fragments in order, so OneDrive uploads use one connection per file; separate files can still upload together. Downloads use parallel byte ranges on every connector.

Pause stops scheduling chunks and aborts in-flight requests. Resume checks server-confirmed upload parts or the browser's disk-backed download journal and requests only missing chunks. Download writes can complete out of order; the journal records each flushed chunk separately so a later chunk cannot disguise gaps as a finished file after refresh. Existing sequential downloads migrate their confirmed prefix. Files are saved only after every chunk and a final access/version check succeed. Download parts remain in this browser until the transfer is removed; uploads require reselecting the original file after refresh.

Each storage coordinator permits up to three independent upload parts or download initializations concurrently; downloads stream their responses. Capacity changes, new upload reservations, completion, cleanup and deletion retain an exclusive barrier; duplicate part writes serialize and validate their digests. Parallelism never bypasses quota, retention, recipient verification or invitation checks. Transfers keep the original part size (8 MiB, or OneDrive's aligned 10 MiB) and request bodies remain below Cloudflare's 100 MB limit.

## Transfer feedback and actions

A completed transfer has a green **Done** badge attached to its card. Uploads show **Finalizing upload…** after all bytes have arrived while File Station waits for storage completion and, for invitations, publication. The Done badge appears only after those operations succeed. Paused and failed uploads retain their progress and controls without a success badge. Completed uploads also show a compact Done badge beside the filename in file lists; this follows the current browser's transfer history and disappears when that history is dismissed, without changing the stored file. Completion messages are announced politely for screen readers and translated into Canadian French and Simplified Chinese.

File lists display two labeled download actions: **Resumable** uses a cloud-download icon and the Transfers panel; **Direct** uses a download-to-device icon and the browser's normal download flow. Recipient previews and collaboration views use the same icon meanings. Transfer navigation uses bidirectional arrows, file requests an inbox, access codes a key, and collaboration a document with a pen. Save-again uses a save icon, in-progress cancellation uses a circled X, and completed transfer dismissal uses a plain X. File-type icons distinguish documents, images, video, audio, spreadsheets, presentations, code and archives.
