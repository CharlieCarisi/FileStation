# Submission requests and collaboration

Signed-in, approved users have **File requests** and **Collaborations** tabs. Create an invitation with recipient email addresses, expiry, storage destination and size limits. You can email it automatically or copy its link/access code. Management shows links, submissions and revocation controls; administrators can view all users' invitations. Download shares continue to work.

The home access form accepts download keys, submission keys (`U…`) and collaboration keys (`C…`). Possessing the code is insufficient: the recipient must verify a PIN delivered to an invited email. External recipients require no approved File Station account. Sessions and every subsequent operation check invitation expiry, revocation and owner status.

Submission partners can upload to the requester-selected connector. They see only their own submissions, with no access to other recipients' files, destination credentials, file listings or download access. File-count and size limits are enforced server-side. Quota/retention apply to submitted files as to ordinary uploads, and the requester owns them.

For collaboration, select an uploaded original and specify a target filename with the same extension. The original remains unchanged. Until the first save, downloads use its bytes with the target name. Saves and re-uploads publish one separate working copy. Subsequent saves replace that working copy and delete the previous one. There is **no version history** or simultaneous keystroke synchronization. Concurrent saves use a compare-and-swap token so a stale editor cannot silently overwrite another person's changes. Download your local edits if a conflict occurs, reopen the current copy, and merge them.

DOCX and UTF-8 plain text (including Markdown/CSV/JSON/XML/YAML) up to 20 MiB can be edited in the browser. DOCX uses the Apache-licensed EigenPal editor; complex Word features may render differently, so review documents in Word when layout fidelity is critical. The editor is loaded on demand, uses local fonts and does not send documents to Microsoft 365 or an external editor server. Larger or unsupported documents can be downloaded, edited on a desktop and re-uploaded. Edits are saved only when **Save working copy** finishes its transfer; unsaved browser edits do not survive refresh. Transfers themselves support pause/resume.

Active collaboration originals and current copies are protected from FIFO eviction so a save cannot evict its own original. There must be space for the old copy and the incoming replacement during a save. Age retention, explicit deletion and owner deactivation can still invalidate collaboration. Expired/revoked links do not grant perpetual access.

## File previews

Verified download recipients and collaboration partners have an inline preview. Images (PNG, JPEG, GIF, WebP, AVIF, BMP), browser-supported video/audio, PDF, DOCX, Excel XLSX/XLS data, PowerPoint PPTX slides and UTF-8 text are supported. Markdown, CSV, JSON, XML, HTML and SVG appear as escaped source text; uploaded markup never executes. Other formats, including legacy Word DOC and PowerPoint PPT files, macro-enabled XLSM/PPTM documents and archives, retain their download options.

Small files up to 10 MiB open automatically. Larger supported files require **Show preview**. Image previews are limited to 25 MiB, PDFs and PPTX to 50 MiB, DOCX and Excel workbooks to 20 MiB, and text to 2 MiB. Video/audio use authenticated byte ranges capped at 8 MiB per response, including seeking on WebDAV-backed storage. Playback depends on the browser's codecs. Hide preview to stop loading or playback. Downloads remain available when a renderer fails or a file is too large.

PDF pages render locally with PDF.js, with page navigation, zoom and an accessible page-text option. DOCX uses the existing editor in read-only mode. Preview code, fonts and PDF resources are served from File Station; no external document viewer receives the files. Every preview/range request rechecks the same recipient authorization, retention and expiry rules as downloading. A collaboration preview refreshes after a saved edit or re-upload, and refuses to show a replacement under an older file identity. Already displayed bytes cannot be withdrawn from a recipient's browser by revoking access.

## Parallel transfers

The transfer panel lets each browser choose **1–3 parallel connections**, with three by default and a shared limit of six active chunk requests across its transfers. A change applies to new or resumed transfers. Use fewer connections for constrained networks. R2, S3, AliPan and WebDAV/Synology uploads can send independent chunks together. Microsoft requires OneDrive upload-session fragments in order, so OneDrive uploads use one connection per file; separate files can still upload together. Downloads use parallel byte ranges on every connector.

Pause stops scheduling chunks and aborts in-flight requests. Resume checks server-confirmed upload parts or the browser's disk-backed download journal and requests only missing chunks. Download writes can complete out of order; the journal records each flushed chunk separately so a later chunk cannot disguise gaps as a finished file after refresh. Existing sequential downloads migrate their confirmed prefix. Files are saved only after every chunk and a final access/version check succeed. Download parts remain in this browser until the transfer is removed; uploads require reselecting the original file after refresh.

Each storage coordinator permits up to three independent upload parts or download initializations concurrently; downloads stream their responses. Capacity changes, new upload reservations, completion, cleanup and deletion retain an exclusive barrier; duplicate part writes serialize and validate their digests. Parallelism never bypasses quota, retention, recipient verification or invitation checks. Transfers keep the original part size (8 MiB, or OneDrive's aligned 10 MiB) and request bodies remain below Cloudflare's 100 MB limit.

## Transfer feedback and actions

A completed transfer has a green **Done** badge attached to its card. Uploads show **Finalizing upload…** after all bytes have arrived while File Station waits for storage completion and, for invitations, publication. The Done badge appears only after those operations succeed. Paused and failed uploads retain their progress and controls without a success badge. Completed uploads also show a compact Done badge beside the filename in file lists; this follows the current browser's transfer history and disappears when that history is dismissed, without changing the stored file. Completion messages are announced politely for screen readers and translated into Canadian French and Simplified Chinese.

File lists display two labeled download actions: **Resumable** uses a cloud-download icon and the Transfers panel; **Direct** uses a download-to-device icon and the browser's normal download flow. Recipient previews and collaboration views use the same icon meanings. Transfer navigation uses bidirectional arrows, file requests an inbox, access codes a key, and collaboration a document with a pen. Save-again uses a save icon, in-progress cancellation uses a circled X, and completed transfer dismissal uses a plain X. File-type icons distinguish documents, images, video, audio, spreadsheets, presentations, code and archives.

## Multiple recipients

File requests, collaboration invitations and download shares accept up to **20 unique email addresses** in one operation. Paste addresses separated by commas, semicolons, spaces or new lines; Chinese comma/semicolon/list separators also work. Addresses are normalized and duplicates are counted once. Invalid addresses are reported before anything is created. API callers can send a recipient string, an array of addresses, or array entries containing separated addresses.

One request or share has one common access code for everyone invited. Each person verifies their own invited email address and receives a separate session. Submission guests can upload with the same code while seeing only their own submissions; the requester sees all submissions. The maximum submission count remains a total across the request. Sign-in and email verification each take one address.

SMTP2GO counts a message addressed to several people as **one successful email**, rather than one success per recipient. File Station requests `fastaccept: false`, checks the message-level success count and failure/error fields, and reports the number of unique recipients in the UI. A genuine provider rejection leaves the created request/share and its recipient permissions intact, so the existing link/code can still be sent manually. There is no automatic resend of existing invitations when deploying this fix. Provider acceptance and final mailbox delivery are separate; SMTP2GO Activity shows the subsequent delivery events.

## Folder ZIPs and folder views

Use the ZIP icon on a folder to **Create and save ZIP**. The archive includes the folder, nested folders (including empty ones), and up to 1,000 ready, unexpired files across their storage connectors. Pending uploads are skipped and remain resumable. ZIP names are safe relative paths; duplicate filenames receive numbered suffixes. Private folder access is restricted to the owner and administrators; approved users can archive Public folders. Each source download rechecks access and expiry.

Choose an enabled, configured destination connector. The ZIP saves beside its source folder in the same workspace as an ordinary file that can be renamed, moved, downloaded and shared. Source files remain in place. ZIP uploads reserve only free capacity and never evict existing files to make room; normal uploads retain the configured FIFO retention behavior.

**Stream to storage (large folders)** creates an uncompressed ZIP64 directly in resumable upload parts without a temporary browser file. It is selected automatically for folders of 256 MiB or more, when browser storage is insufficient (including zero current usage), or when private file storage is unavailable. This works in Firefox, Chrome, Edge and Safari and avoids origin disk quotas for large folders such as 10 GB of video. One ZIP part is prepared/uploaded at a time, with source range reads capped at 8 MiB and a part capped at 10 MiB for the current connectors. The exact final size is calculated before downloading sources, so ordinary connector capacity reservations protect originals. Video files are already compressed and usually gain little from ZIP compression.

Streaming ZIPs appear immediately in **Transfers**, where creation and upload can be paused, resumed or cancelled together. The browser saves the manifest and small CRC checkpoints rather than file contents. Resume after a page refresh in the same browser/site skips server-accepted parts and previously read source ranges; it needs no desktop file. Originals that have not yet been read must remain accessible and unexpired. Cancellation removes the incomplete ZIP upload and keeps the originals. Completion discards the saved manifest/checkpoints. Clearing browser site data removes the resume metadata.

**Compress using browser storage** remains available for smaller folders or when reducing size matters. It streams authenticated ranges into a temporary ZIP on private browser disk, with ZIP64 and native compression. Keep the tab open during creation; Cancel discards the partial archive. After creation, its upload supports pause/resume after refresh without selecting a desktop file because the temporary source is kept until completion or cancellation. Creating this compressed ZIP itself restarts if interrupted. A quota error directs users to Stream to storage. Both modes use the destination connector's normal expiry/retention policy.

The **Tiles / List** toggle beside New folder persists in the current browser. List places folders above files in the same table, with ZIP, manage and delete actions; selecting files for bulk moves still selects files only. Search filters folder names as well as files in the current folder. Logical folders remain independent of physical storage connectors.

## Recipient guidance

The public page centers the access-code form, explains that no account is needed, and keeps Sign in in the header. A visible three-step indicator follows code/email entry, email verification and the invited action. **How to upload files** opens an inline guide on the landing page and in submission requests, including choosing documents, automatic upload, pause/resume and waiting for Done. Download and collaboration views have matching contextual guides. The access card appears first on mobile. All new controls and guidance are available in Canadian French and Simplified Chinese.

## Preview windows

Ready files in Private, Public, Shared by me, and administrative file lists have an **eye icon** when their format and size support previewing. It opens a dedicated preview window, keeping the file browser and its transfers in place. Existing recipient and collaboration previews also have **Open in new window**. Browser preferences can open these links in a tab instead; modified clicks and the link context menu retain normal browser behavior.

The window uses the same local image, media, PDF, read-only DOCX and escaped text/code viewers and format limits described above. Explicitly opening a window loads the supported preview immediately, including media larger than the inline auto-open threshold. It provides refresh, close, language and direct-download controls where the storage supports direct downloads. For large chunk-backed WebDAV/Synology files, use resumable download in the original window. Preview windows do not create or overwrite transfer history.

The window loads metadata through the same file/share permission checks as file bytes. Metadata exposes only the filename, size, MIME type, expiry, ID and storage type. It contains no share codes, credentials or provider URLs. Cookies remain on the current origin; preview links work at both supported File Station addresses. An unverified, expired or revoked session cannot open private content. Each content request also rechecks access. Collaboration windows use the invitation's current working copy and version checks; use **Refresh preview** to load a newly saved revision. Existing preview bytes may remain visible until refreshed or closed.


## Excel and PowerPoint

Excel **.xlsx** and legacy **.xls** open as read-only worksheet data in the same preview windows, recipient views and collaboration views. Switch visible worksheets and page through rows and columns. Saved currency, date, percentage and other number formats are preserved; formulas use cached saved results or show their formula text when no value was saved. Merged cells are retained within the displayed page. Charts, images and advanced formatting are not rendered, and no formulas or macros execute. Hidden worksheets are omitted.

A workbook may contain up to 100 sheets. Preview is limited to the first **20,000 rows and 200 columns per sheet**, displaying at most 100 rows and 25 columns at a time; larger used ranges show a truncation notice. Cell text is capped at 4,000 characters. Parsing runs in a disposable browser worker with a 20-second limit; closing or hiding the preview terminates it. Password-protected, damaged or overly complex workbooks keep their download option. The maintained SheetJS 0.20.3 vendor tarball is pinned in the lockfile.

PowerPoint **.pptx** uses the Apache-licensed `@aiden0z/pptx-renderer` 1.4.0 with previous/next and direct slide selection, lazy slides and embedded media. Text, embedded images, shapes, tables and supported charts render locally. Layout and font fidelity can differ from PowerPoint; animations, transitions and linked content do not play. Legacy **.ppt** must be converted to **.pptx** before previewing. Presentations are limited to 300 slide parts; a 30-second preview timeout retains the download option.

The presentation renderer runs in an opaque iframe sandbox with no same-origin privilege, API connections, external media, popups or navigation through document links. Only the trusted renderer page (`presentation-preview`) can be embedded from File Station. Public script/style assets allow anonymous CORS and GET/HEAD preflight so that frame can load its bundled modules; authenticated APIs keep their existing same-origin rules. The parent fetches authorized file bytes and sends them to that frame without provider URLs or session tokens. Office ZIP directories are checked before parsing, with a 4,000-entry cap, a 50 MiB per-entry cap and a 200 MiB expanded-size cap; the presentation parser also enforces decode limits. Third-party notices are served under `licenses/`.

These are preview additions. Excel and PowerPoint collaboration still uses desktop editing and re-upload; the existing online editor supports DOCX and text. All new controls and messages are translated into Canadian French and Simplified Chinese.
